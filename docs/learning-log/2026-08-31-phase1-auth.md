# Phase 1 — Auth: register, login, middleware, trust-device, refresh, logout, password reset

This is the tutorial version of what we built today. It covers the same ground as the
in-chat explanations, but organized as one document you can come back to. It's written for
someone comfortable with JS/TS/React who is new to C#, ASP.NET Core, EF Core, and
ASP.NET Core Identity — new concepts are explained the first time they show up, and
compared to the closest TypeScript/Node equivalent where that helps.

**Where the code lives**, if you want to read along:
- Backend: `backend/MySelf.Api/Auth/`, `backend/MySelf.Api/Me/`, `backend/MySelf.Infrastructure/Identity/`, `backend/MySelf.Domain/Identity/`
- Frontend: `frontend/src/features/auth/`, `frontend/src/app/`

## 0. Concepts you'll see over and over

Read this section once; the rest of the doc assumes you know these words.

**ASP.NET Core Identity** — Microsoft's built-in library for "users, passwords, and
account state." It's not a REST API or a UI — it's a set of C# classes
(`UserManager<TUser>`, `IdentityUser<TKey>`, `IdentityResult`, ...) that handle hashing
passwords, checking uniqueness, tracking failed login attempts, and generating
security tokens. Closest analogy: if you'd hand-rolled an `AuthService` around `bcrypt`
plus a `users` table yourself, Identity *is* that service, already written and tested.

**`UserManager<TUser>`** — the main object you talk to. Injected via DI (see below) into
any endpoint that needs it. Methods like `CreateAsync`, `FindByEmailAsync`,
`CheckPasswordAsync`, `GeneratePasswordResetTokenAsync` all live here.

**Minimal APIs** — the routing style this project uses instead of MVC controllers. A route
is just `app.MapPost("/path", HandlerMethod)`. The handler's parameters are populated by
the framework based on their *type*, not their order — `HttpRequest`, `HttpResponse`,
`CancellationToken`, and anything registered in DI (like `UserManager<ApplicationUser>`)
are recognized automatically; anything else is assumed to be the JSON request body.

**Dependency Injection (DI)** — instead of `new SomeService()` inside a method, you declare
"this app has one of these" in `Program.cs` (`builder.Services.AddScoped<TokenService>()`,
etc.), and the framework hands you an instance wherever you ask for that type — as a
constructor parameter, or (in Minimal APIs) as a handler parameter. Same idea as a React
Context provider handing a value to whatever component asks for it via `useContext`,
except DI works for backend services instead of UI state, and the "provider" is
`Program.cs`.

**Middleware pipeline** — every HTTP request passes through an ordered chain of
`app.Use...()` calls before reaching your endpoint (and the response passes back through
in reverse). Directly equivalent to Express middleware (`app.use(...)`). Order matters:
`UseAuthentication()` has to run before `UseAuthorization()`, which has to run before your
endpoint, or there's nothing for the later step to check yet.

**JWT (JSON Web Token) & claims** — a JWT is a signed, self-contained string that encodes a
set of key/value pairs ("claims", e.g. `sub` = user id, `email` = ...). "Signed" means
anyone can *read* it (it's just base64), but only the server holding the secret key can
*produce a validly-signed one* — so the server can trust a claim inside a token it
receives back, without a database lookup, as long as the signature checks out. That's why
access tokens are called "self-contained": no DB round-trip is needed to know who's
calling, only to check who's *allowed*.

**Cookies: `HttpOnly` / `Secure` / `SameSite` / persistent vs. session** —
- `HttpOnly`: JavaScript (`document.cookie`) can't read it — only the browser sends it
  automatically on requests. Defends against XSS stealing it.
- `Secure`: only sent over HTTPS.
- `SameSite=Lax`: sent on top-level navigation and "safe" cross-site requests, blocked for
  most cross-site POSTs — a CSRF mitigation.
- **Persistent vs. session cookie**: a cookie with an `Expires`/`Max-Age` attribute survives
  a browser restart ("persistent"). One with *no* `Expires` at all is a "session cookie" —
  the browser deletes it the moment the browser itself closes (not just the tab). This
  distinction is the entire mechanism behind "trust this device" (§5).

**EF Core migrations** — you change a C# entity class, run `dotnet ef migrations add Name`,
and EF Core diffs your classes against its last-known snapshot to generate a C# file with
the SQL (`CreateTable`, `AddColumn`, ...) needed to catch the database up. `dotnet ef
database update` actually runs it. Same job as a Prisma/Knex migration, but the "diff"
step is done by comparing C# class shapes, not by you hand-writing SQL.

## 1. Register — `POST /api/v1/auth/register`

### Files

| File | What it is |
|---|---|
| `MySelf.Infrastructure/Identity/ApplicationUser.cs` | Identity's user row: `class ApplicationUser : IdentityUser<Guid>` |
| `MySelf.Infrastructure/Persistence/MySelfDbContext.cs` | Base class changed from `DbContext` to `IdentityUserContext<ApplicationUser, Guid>` |
| `MySelf.Api/Auth/RegisterRequest.cs`, `AuthResponse.cs` | Request/response shapes (plain C# `record`s — see below) |
| `MySelf.Api/Auth/AuthEndpoints.cs` | The actual `RegisterAsync` handler |
| `MySelf.Api/Program.cs` | Registers Identity (`AddIdentityCore`) |
| Migration `AddIdentityAndRefreshTokens` | Creates `AspNetUsers` + related tables |

### New concept: `record`

```csharp
public sealed record RegisterRequest(string? Username, string? Email, string? Password, bool TrustThisDevice = false);
```

A `record` is a class built for holding immutable data — you get a constructor,
value-based equality, and a nice `ToString()` for free. It's C#'s answer to a TypeScript
`type`/`interface` used as a DTO, except it also generates working object identity
(`recordA == recordB` compares values, not references, unlike a plain `class`).

### New concept: why `ApplicationUser` lives in `Infrastructure`, not `Domain`

`MySelf.Domain` has zero NuGet package references on purpose — it's meant to be plain C#
describing the business, not tied to any framework. `IdentityUser<TKey>` comes from a
Microsoft package. So `ApplicationUser` (which *is* an `IdentityUser`) lives in
`Infrastructure` instead, keeping `Domain` framework-free. Contrast with `docs/04`'s
`UserProfile`/`UserGoal` — those *will* live in `Domain` later (onboarding slice), because
they're pure business data with no framework dependency.

### New concept: `IdentityUserContext` vs `IdentityDbContext`

```csharp
public class MySelfDbContext(DbContextOptions<MySelfDbContext> options)
    : IdentityUserContext<ApplicationUser, Guid>(options)
```

`IdentityDbContext` adds Users **and** Roles/RoleClaims tables. `IdentityUserContext` is
the lighter variant — just Users/Claims/Logins/Tokens. This app has no role-based
authorization requirement (only per-owner checks), so the Roles tables would be dead
weight — picked the smaller one deliberately.

### The handler, walked through

```csharp
var user = new ApplicationUser { UserName = request.Username, Email = request.Email };
var createResult = await userManager.CreateAsync(user, request.Password!);
```

`CreateAsync` does a lot in one call: normalizes the email/username, checks both are
unique, validates the password against the configured policy, hashes it (never stores
plaintext), and inserts the row — all inside its own transaction. It returns an
`IdentityResult` — think of it like a Zod `safeParse()` result: `{ Succeeded, Errors[] }`
instead of throwing.

On success, `IssueSessionAsync` (shared with login — see §3) builds a JWT, creates a
refresh token, and sets the cookie. The endpoint returns `201 Created`.

### Request flow

```
POST /register {username, email, password}
  → RegisterAsync
      → userManager.CreateAsync(user, password)   — hash + uniqueness + INSERT
      → IssueSessionAsync
          → tokens.CreateAccessToken(user)         — signs a JWT
          → tokens.CreateRefreshToken()             — random string + its SHA-256 hash
          → db.RefreshTokens.Add(...) + SaveChangesAsync
          → response.Cookies.Append("refreshToken", ...)
  ← 201 { accessToken, accessTokenExpiresAt, user }
```

### A real bug we hit and fixed: friendly error messages

Identity's default error for a bad username literally says *"...can only contain letters
or digits"* — which became a lie the moment we customized the allowed character set to
also permit `_`, `.`, `-`. `AuthEndpoints.GroupByField` substitutes an accurate message for
that specific error code instead of shipping the wrong one:

```csharp
var description = error.Code == "InvalidUserName"
    ? "Only letters, numbers, dots, underscores and hyphens are allowed."
    : error.Description;
```

Lesson: a framework's default error text is a starting point, not gospel — check it
actually matches what you configured.

## 2. Login — `POST /api/v1/auth/login`

### Files
`MySelf.Api/Auth/LoginRequest.cs`, and the `LoginAsync` handler in `AuthEndpoints.cs`.

### Login by username *or* email

```csharp
var user = identifier.Contains('@')
    ? await userManager.FindByEmailAsync(identifier)
    : await userManager.FindByNameAsync(identifier);
```

This only works safely because usernames are *guaranteed* not to contain `@` — that
restriction was set on purpose in `Program.cs`'s `AllowedUserNameCharacters` specifically
so this check would be unambiguous later. Small decision made early, paid off here.

### New concept: account lockout

```csharp
if (await userManager.IsLockedOutAsync(user)) { ... return 423 Locked ... }
if (!await userManager.CheckPasswordAsync(user, request.Password))
{
    await userManager.AccessFailedAsync(user);   // counts toward the lockout threshold
    return InvalidCredentials();
}
await userManager.ResetAccessFailedCountAsync(user);
```

Identity tracks `AccessFailedCount` and `LockoutEnd` columns on the user row for you.
`AccessFailedAsync` increments the counter and — once it crosses the configured threshold
(`Program.cs`: 5 attempts) — sets `LockoutEnd` automatically. `IsLockedOutAsync` just
checks whether `LockoutEnd` is still in the future. None of this required us to write our
own counting logic.

### Why "invalid credentials" never says which part was wrong

```csharp
if (user is null) { return InvalidCredentials(); }
// ...
if (!await userManager.CheckPasswordAsync(user, request.Password))
{
    return InvalidCredentials();  // same response as "user is null"
}
```

Both "no such account" and "wrong password" return the exact same `401` with the exact
same message. If they were different, an attacker could feed in emails and learn from the
response which ones have accounts — "account enumeration." Same reasoning shows up again
in password reset (§6).

## 3. JWT-bearer middleware + `GET /api/v1/me`

This is where "issuing tokens" and "checking tokens" become two separate, deliberately
sequenced things.

### Files
`MySelf.Api/Program.cs` (middleware registration), `MySelf.Api/Me/MeEndpoints.cs`.

### Registering the middleware

```csharp
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true, ValidIssuer = jwtOptions.Issuer,
            ValidateAudience = true, ValidAudience = jwtOptions.Audience,
            ValidateIssuerSigningKey = true,
            IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(jwtOptions.Key)),
            ValidateLifetime = true,
            ClockSkew = TimeSpan.FromSeconds(30),
        };
    });
builder.Services.AddAuthorization();
```

```csharp
app.UseAuthentication();   // WHO is calling? Reads the Authorization header, validates
                            // the JWT signature/issuer/audience/expiry, populates HttpContext.User
app.UseAuthorization();    // Is this caller ALLOWED here? Checks .RequireAuthorization()
```

These are two different questions and two different middlewares on purpose.
Authentication can succeed (valid token) while authorization still says no (e.g., wrong
role) — that distinction doesn't matter much yet in this app (no roles), but the
separation is standard ASP.NET Core shape.

### A gotcha we hit: claim renaming

By default, `JwtSecurityTokenHandler` silently remaps standard claim names on the way in —
`"sub"` becomes a long legacy Microsoft URI
(`http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier`). If we hadn't
disabled that, `TokenService` would write `"sub"` onto the token, and
`MeEndpoints` reading `JwtRegisteredClaimNames.Sub` back out would find nothing. Fixed with
one line at the very top of `Program.cs`:

```csharp
JwtSecurityTokenHandler.DefaultMapInboundClaims = false;
```

This is a well-known .NET JWT trap — worth remembering for any future JWT work.

### The protected endpoint itself

```csharp
app.MapGet("/api/v1/me", GetMeAsync).RequireAuthorization();

private static async Task<IResult> GetMeAsync(HttpContext httpContext, UserManager<ApplicationUser> userManager)
{
    var userId = httpContext.User.FindFirst(JwtRegisteredClaimNames.Sub)?.Value;
    var user = userId is null ? null : await userManager.FindByIdAsync(userId);
    ...
    return Results.Ok(new AuthUser(user.Id, user.UserName!, user.Email!));
}
```

`.RequireAuthorization()` is the whole "protect this route" mechanism — without it, any
route is public by default. `httpContext.User` is populated by `UseAuthentication` from the
JWT before the handler ever runs.

## 4. "Trust this device" + `POST /api/v1/auth/refresh`

This was the biggest conceptual piece. The literal request was "put it in localStorage if
trusted" — we didn't do that, and it's worth understanding why, and what we did instead.

### Why not `localStorage`

`docs/05` (the security spec) states plainly: *"short-lived access token kept in memory...
no auth token in localStorage."* `localStorage` is readable by any JavaScript running on
the page — including injected/malicious script (XSS). An `HttpOnly` cookie is not
readable by JavaScript at all. Same end-user goal ("stay logged in"), safer mechanism.

### The actual mechanism: persistent vs. session cookie

```csharp
private static void SetRefreshCookie(HttpResponse response, string rawToken,
    DateTimeOffset expiresAt, bool persistent, IHostEnvironment env)
{
    var options = CookieAttributes(env);   // HttpOnly, Secure (prod), SameSite=Lax, Path
    if (persistent)
    {
        options.Expires = expiresAt;       // survives browser close
    }
    // else: no Expires set at all → browser drops it when the browser itself closes
    response.Cookies.Append("refreshToken", rawToken, options);
}
```

Checking "Trust this device" just flips `persistent`. Nothing about the *token* changes —
only whether the browser is told to remember the cookie past this browsing session.

### New DB column: `RefreshToken.IsPersistent`

```csharp
public bool IsPersistent { get; set; }
```

Needed because `/refresh` **rotates** the token (next section) — the replacement cookie
has to know whether to also be persistent or session-only, and that information has to
survive on the server between requests, so it's stored alongside the token row.

### Rotation: why a refresh token is single-use

```csharp
existing.RevokedAt = now;   // the OLD token, marked dead
var session = await IssueSessionAsync(user, existing.IsPersistent, ...);  // a NEW one issued
```

Every successful `/refresh` call kills the token it was given and hands back a brand new
one. If someone ever steals a refresh cookie (log leak, XSS despite `HttpOnly`, whatever),
the moment the *real* user's browser refreshes, the stolen copy stops working — it's
already revoked. This is what `docs/05`'s phrase "rotating refresh token" means concretely,
and it's exactly what `RefreshEndpointTests.Rotated_cookie_cannot_be_reused` checks.

### Silent refresh on frontend app load

`frontend/src/features/auth/AuthContext.tsx`:

```tsx
useEffect(() => {
  apiFetch<RefreshResponse>("/api/v1/auth/refresh", { method: "POST" })
    .then((result) => { setSessionState(...); setStatus("authenticated"); })
    .catch(() => { setStatus("unauthenticated"); });
}, []);
```

Every time the app boots (page load, browser reopened), it silently tries `/refresh`. If a
persistent cookie is still there, this succeeds and the user lands on the dashboard
without seeing the login form at all. If not (never checked "trust this device", or the
browser was actually closed), it fails quietly — that's just "not logged in," not an
error. `RequireAuth`/`RedirectIfAuthenticated` both wait for a third status,
`"loading"`, so the app doesn't flash the login screen before this check resolves.

## 5. `POST /api/v1/auth/logout`

```csharp
if (request.Cookies.TryGetValue("refreshToken", out var rawToken) && !string.IsNullOrEmpty(rawToken))
{
    var existing = await db.RefreshTokens.FirstOrDefaultAsync(t => t.TokenHash == TokenService.Hash(rawToken), ct);
    if (existing is not null && existing.RevokedAt is null)
    {
        existing.RevokedAt = DateTimeOffset.UtcNow;
        await db.SaveChangesAsync(ct);
    }
}
response.Cookies.Delete("refreshToken", CookieAttributes(env));
return Results.NoContent();
```

Two separate things happen: the token is revoked **server-side** (so even if someone
copied the cookie value earlier, it's now dead), and the cookie is cleared
**client-side** (`Cookies.Delete` — this only works if the `Path`/`HttpOnly`/etc.
attributes match what was used to set it originally, which is why both `SetRefreshCookie`
and `LogoutAsync` share one `CookieAttributes()` helper).

It's deliberately idempotent — no cookie, or an already-revoked one, still returns success.
Calling logout twice, or with a stale tab, should never be an error.

On the frontend, `useLogout.ts` clears the in-memory session in `onSettled` (runs whether
the network call succeeded *or* failed) rather than `onSuccess` — even if the logout
request itself fails (network blip), the user's local session still needs to end. Clearing
`session` flips `RequireAuth`'s status to `"unauthenticated"`, which redirects to
`/login` — no explicit `navigate()` call needed, it falls out of the existing guard.

## 6. Password reset (dev-sink)

### Files
`MySelf.Api/Auth/PasswordResetEndpoints.cs`, `PasswordResetRequests.cs`.

### The dev-sink idea

`docs/05` anticipated exactly this: *"email verification/reset can initially write a dev
link to a safe local sink"* before a real email provider exists. So instead of sending an
email:

```csharp
var token = await userManager.GeneratePasswordResetTokenAsync(user);
var resetLink = $"{frontendBaseUrl}/reset-password?email={Uri.EscapeDataString(user.Email!)}&token={Uri.EscapeDataString(token)}";
logger.LogInformation("Password reset link for {Email}: {ResetLink}", user.Email, resetLink);
return Results.Ok(new ForgotPasswordResponse(GenericSentMessage, env.IsDevelopment() ? resetLink : null));
```

The link is logged, and — **only** when `IHostEnvironment.IsDevelopment()` is true — also
handed straight back in the response so you can click it without digging through logs.
In a real deployment, `resetLink` is always `null`, and whatever really sends the email
(a future slice) is the only thing that would need to change — the token/contract stays
identical.

### A real bug this slice caught: missing token provider

The very first run threw a `500` on `GeneratePasswordResetTokenAsync`. Cause:
`AddIdentityCore<ApplicationUser>()` registers `UserManager` and friends, but — unlike its
bigger sibling `AddIdentity()` — it does **not** automatically wire up the token providers
that `GeneratePasswordResetTokenAsync`/`ResetPasswordAsync` need internally. Fix, one line
added to the `AddIdentityCore` chain in `Program.cs`:

```csharp
.AddDefaultTokenProviders();
```

This is exactly the kind of thing that's very easy to forget once and very confusing to
debug later — worth remembering: **`AddIdentityCore` is the deliberately minimal Identity
setup; if a "generate a token for X" Identity method throws, this is the first thing to
check.**

### Why a reset also revokes other sessions

```csharp
await db.RefreshTokens
    .Where(t => t.UserId == user.Id && t.RevokedAt == null)
    .ExecuteUpdateAsync(setters => setters.SetProperty(t => t.RevokedAt, DateTimeOffset.UtcNow), ct);
```

`ExecuteUpdateAsync` (EF Core 7+) runs a single `UPDATE ... SET "RevokedAt" = @now WHERE
...` directly in the database — no need to load every row into memory first just to change
one column, which is the older/slower EF pattern. The reasoning: if you're resetting your
password, it's often *because* something was compromised (or a device someone else had
access to was logged in) — wiping every other active session is a standard defensive
move, not just cleanup.

## 7. Frontend companion pieces (brief tour)

- **`lib/api.ts`** — the one `fetch` wrapper everything routes through.
  `credentials: "include"` is what makes the browser actually attach/receive the
  `HttpOnly` cookie across the frontend (5173) ↔ API (5242) origin boundary. `ApiError`
  normalizes both of the backend's error shapes (`ProblemDetails` → `.detail`;
  `ValidationProblemDetails` → `.errors`) into one type screens can branch on.
- **`features/auth/auth.ts` + `AuthContext.tsx`** — split the same way `app/theme.ts` /
  `ThemeProvider.tsx` already were in this codebase (context + hook in one file, the
  provider component in another) — required by an ESLint rule (`react-refresh/only-export-
  components`) that flags a file exporting both a component and a non-component value.
- **`app/RequireAuth.tsx`** / **`RedirectIfAuthenticated.tsx`** — two small route guards,
  mirror images of each other, both waiting out the `"loading"` status before deciding.
- **`components/ui/PasswordInput.tsx`** — a `forwardRef`-wrapped `<input>` with a show/hide
  toggle. It has to forward its `ref` because React Hook Form's `register("password")`
  spreads a `ref` callback onto whatever it's attached to, and that has to land on the
  real DOM `<input>`, not on the wrapper component.

## 8. Full picture: one request, start to finish

```
Browser                          Frontend (5173)                    API (5242)                Postgres
   │                                   │                                  │                        │
   │ opens app                        │ AuthProvider mounts             │                        │
   │                                   │ POST /auth/refresh (cookie) ───▶│ hash lookup ──────────▶│
   │                                   │◀── 200 {accessToken, user} ─────│ rotate + new row ◀─────│
   │                                   │ status="authenticated"          │                        │
   │                                   │                                  │                        │
   │ clicks "Log meal" (protected)    │ GET /api/v1/... 
   │                                   │   Authorization: Bearer <token>▶│ UseAuthentication:      │
   │                                   │                                  │   validate JWT sig,     │
   │                                   │                                  │   populate User claims  │
   │                                   │                                  │ UseAuthorization: OK    │
   │                                   │◀── 200 {...} ────────────────────│ handler runs            │
   │                                   │                                  │                        │
   │ clicks "Log out"                 │ POST /auth/logout ──────────────▶│ revoke token row ──────▶│
   │                                   │◀── 204, cookie cleared ──────────│                        │
   │                                   │ setSession(null) → RequireAuth  │                        │
   │                                   │   redirects to /login           │                        │
```
